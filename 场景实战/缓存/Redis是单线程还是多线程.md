# Redis 是单线程还是多线程

> 短答：**命令执行是单线程**，**网络 IO 是多线程**（6.0+）。


---

## 这是怎么演进的

```
Redis 1.x ~ 5.x：           Redis 6.0+：
  全单线程                    网络 IO 多线程，命令执行仍单线程
  ┌──────────────┐           ┌──────────────┐
  │ Main Thread  │           │ IO Thread 1  │ ─┐
  │ ├ 网络读      │           │ IO Thread 2  │ ─┼─→ ┌─────────────┐
  │ ├ 解析        │           │ IO Thread 3  │ ─┤   │ Main Thread │
  │ ├ 执行        │           │ IO Thread 4  │ ─┘   │ 执行命令     │
  │ └ 网络写      │           └──────────────┘     │ （还是单线程）│
  └──────────────┘                                └─────────────┘
```

为什么 6.0 要加多线程网络 IO？
- 高 QPS 下，网络 IO（read/write/解析）耗时 > 命令执行耗时
- 多线程做 IO 把这部分时间分摊掉
- **命令执行保持单线程，保留无锁优势**

---

## IO 多路复用：单线程为什么能扛十万 QPS

```
传统 BIO（每连接一线程）：             多路复用（一个线程盯所有连接）：

  conn1 ─→ Thread1                      conn1 ─┐
  conn2 ─→ Thread2                      conn2 ─┤
  conn3 ─→ Thread3                      conn3 ─┼─→ epoll ─→ Thread
   ...                                  conn4 ─┤            就绪谁就处理谁
  conn1万 ─→ Thread1万                  ...   ─┘

  痛点：线程切换、内存爆炸             优势：1 个线程管几万连接
```

epoll 的核心：内核帮你监听一堆 fd，谁有数据就回调谁，**线程只处理"就绪的"**。

---

## Redis 单线程为什么这么快


| 原因 | 解释 |
| :--- | :--- |
| **纯内存** | 内存读写 ~100ns，磁盘 ~10ms，差 5 个数量级 |
| **IO 多路复用** | 单线程也能监听几万连接 |
| **避免锁** | 单线程天然无并发问题，省掉加锁解锁开销 |
| **避免上下文切换** | 多线程 CPU 时间常浪费在切换上 |
| **高效数据结构** | dict（渐进 rehash）、ziplist、skiplist、quicklist 全是为速度设计 |

## 单线程的代价：怕慢命令

```
┌────────────────────────────────────┐
│ Redis 主线程时间轴                  │
│   ─cmd1─ ─cmd2─ ─KEYS *─ ─cmd3─    │
│                  ↑↑↑↑                │
│              一条 KEYS 卡住          │
│         后面所有命令排队等           │
└────────────────────────────────────┘
```

**禁忌命令**：
- `KEYS *` → 用 `SCAN` 替代
- `FLUSHALL`、`FLUSHDB` → 用 `FLUSHALL ASYNC`
- 大 key 的 `HGETALL`、`SMEMBERS` → 用 `HSCAN`、`SSCAN`
- 复杂的 Lua 脚本（循环 10 万次）

> 一句话：**任何 O(n) 操作都得当心**，n 可能比你想的大得多。

---

## 总结

- **执行 = 单线程**：保证数据结构操作的原子性，无锁极速
- **网络 = 多线程**（6.0+）：榨干网卡性能
- **快的根源**：纯内存 + epoll + 无锁 + 紧凑结构，不是因为单线程"省"
